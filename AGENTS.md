# Computer

A persistent Linux computer that agents drive and a human can take the seat of. npm workspaces monorepo: `apps/hub` (TypeScript hub), `apps/web` (Next.js 16 on Vercel), `apps/eve` (eve.dev agent, runs beside the hub), `apps/whatsapp-bridge` (Baileys WhatsApp socket, runs beside the hub), `apps/clock` (the always-on Fly app that wakes suspended computers for their routines), `apps/desk` (Debian guest image), `packages/shared` and `packages/proto`.

## Commands

- `npm install` (Node 24; `prepare` installs the lefthook pre-commit hook)
- `npm run check`: typecheck every workspace, layer lint, `ultracite check` (oxlint + oxfmt), knip, hub tests, proto check. CI runs this same command.
- `npm run fix`: format and autofix (`ultracite fix`)
- `npm test`: hub tests (vitest). One file: `npx vitest run test/computer.test.ts --reporter=dot` from `apps/hub`
- `npm run typecheck`: all workspaces; one: `npm run typecheck --workspace=apps/hub`
- `npm run proto:check` after editing `api/computer.proto`: it must be byte-identical to `packages/proto/computer.proto`, then `npm run proto:gen` and commit `packages/proto/gen`
- `npm run up`: local box (needs a Docker daemon; falls back to a fake desk). `npm run web`: Next dev on :3000 against the local hub on :8787
- `npm run bot -- new|ls|rm <id>`: provision Bots against a running hub; `npm run bot -- connector add|ls|rotate|rm` edits `connectors.json`
- `npm test --workspace=apps/eve`: the shared Eve lib (channel, format-reply); `npm test --workspace=apps/whatsapp-bridge`: the bridge; `npm test --workspace=apps/clock`: the outer routine clock (both `node --test`)

## Contract

`api/DESIGN.md` is the source of truth for the wire; `api/spec.json` is what a model loads; `packages/shared/src/index.ts` holds the types and error codes. Change all three together. The hub speaks the proto's RPC names as plain JSON POST, not Connect binary; a buf-generated client cannot talk to it.

## Gotchas

- Hub layering is `handler -> service -> desk`; `scripts/lint-layers.mjs` fails the build on an upward import. Put HTTP parsing in `handler`, rules in `service`, `docker exec`/XTEST in `desk`.
- The model's five tools (`send_message`, `computer`, `shell`, `read_file`, `write_file`) are the whole model surface. Clipboard, `vnc_url`, pointer and provisioning are Seat RPCs only; adding them to the model is the injection path `api/DESIGN.md` refuses.
- Coordinates are integer pixels of the last full 1280x800 screenshot, origin top-left, and `zoom` does not change that space. Never introduce normalised 0..999 coordinates.
- A `computer` batch is validated whole before anything runs; a limit violation is a 400 for the request. Do not move per-action limits back into the execution loop, or a partially-run batch becomes unretryable under its `request_id`.
- Human input is never RFB: x11vnc runs `-viewonly`, and every pointer/keystroke goes through `Seat.Pointer`/`Seat.Type` so the seat FSM can refuse it.
- `apps/eve` files import each other with `.ts` extensions (`allowImportingTsExtensions`); `eve build` bundles them. A bot dir like `apps/eve/bots/main` re-exports from `../../lib`.
- **A Bot is a directory, and shipping one is a deploy.** Root `workspaces` globs `apps/eve/bots/*`, the guest image builds every project under it, and `ensureRoster` mints a row and a token for any project that has no roster row, on the lowest free screen (`eveProjectIds` in `host/eve.ts`). So `Seat.CreateBot` is still how a Bot is made at runtime, but the eight in the image need no RPC at all. Two consequences: a project past the last free screen boots with a warning and no screen (`MAX_DISPLAYS`, now 16, of which the build ships 8); and `DeleteBot` on a Bot whose project is still in the image frees its screen only until the next boot, so removing one for good means removing its directory. The roster is never pruned by init: a Bot whose project is gone keeps its screen, its token and its thread until a person deletes it.
- `agent/profile.json` in a Bot's project is a **seed, not a default**: `BotState.init` writes it to `/workspace/.bots/<id>/profile.json` only when the box has no profile for that Bot, so a rename by the human or by the Bot itself survives every later deploy. A bad shape or colour in a seed degrades to the hashed default rather than failing the boot. `AVATAR_SHAPES` and `AVATAR_COLORS` are append-only and lower case: dropping an entry, or changing its case, silently falls every Bot wearing it back to the default. They are mirrored in `apps/web/lib/seat.ts` (with clip paths in `components/bot-mark.tsx`), so change both.
- A webhook is the other half of a routine: `lib/channels/webhook.ts`, mounted as `agent/channels/<kind>.ts`, reached through a connector (`npm run bot -- connector add <id> <kind> <bot>`), never a direct door. Its payload is a stranger's text, fenced as `<untrusted_context>` with its own fences neutralised, and the route answers 202 rather than the turn's text. The ingress binds a conversation for `whatsapp` only, so a webhook records nothing and the Bot's `send_message` lands in the owner's seat thread; a `webhook` route is the fix and it is a contract change.
- hello.expert is the control plane, and the **account** is the tenant boundary: a signed-in email is bound to one computer (hub URL + seat) through `COMPUTER_BINDINGS`. Blode is `mblode-computer`; Vibey is `vcmc-computer`, a separate login, not a Bot on Blode. Both lookups in `apps/web/lib/computers.ts` fail closed: an email with no binding gets **no** computer (set `DEFAULT_COMPUTER_ID` to opt every unbound account into one), and `COMPUTER_OPERATOR_EMAILS` unset means **nobody** may switch computers or mint invites, so list yourself there or you keep only your bound computer. Set `AUTH_ALLOWED_EMAILS` on any deployment that is not private.
- On the Fly guest the hub runs as user `hub`, not `box`: `/workspace/.computer` (roster, seat tokens, connector secrets, Eve secret, Baileys credentials) is hub-owned at 0700 and the model's `shell` cannot read it. Desk commands run as `box` through `sudo -u box` (`asBox` in `apps/hub/src/desk/docker.ts`, enabled by `COMPUTER_RUN_AS=box`, one line in `/etc/sudoers.d/hub`). `COMPUTER_SETUP_CODE` must be a Fly secret; init refuses to mint one on a cloud deployment.
- The bridge has two kinds of credential and they are not interchangeable. `WHATSAPP_BRIDGE_SECRET` is the **admin** one the hub holds: it opens every route for every account, and it is the only thing that may touch `/accounts`. Each account also carries its own `bridge_secret`, minted into `accounts.json` (and by boot, for a file written before they existed), which opens the data routes for that account alone. `acct` comes from the credential, never from the query or body, and a request naming a different account is a 403: with one shared secret and `acct` read off the request, any holder could read any account's messages, which is invisible on a single-tenant loopback bridge and a cross-tenant read the moment one bridge serves two. `hub_url` on the same record is what lets it: set it to the tenant's **public** Fly hostname, never `<app>.internal`, because only Fly Proxy starts a suspended Machine and a 6PN request reaches a hibernated tenant as a connection error rather than a wake. See `docs/plans/gateway.md`.
- A tenant can be created rather than declared: `apps/hub/src/host/fly-provision.ts`, `npm run machine -- create <app> <org> <image>`, which makes the app, the volume and the Machine. Every computer is the same computer, so the spec is three fields and the guest size, region, volume size and suspend behaviour are constants rather than settings. There is no `env` parameter, deliberately: Fly delivers app secrets as environment variables, so a setup code passed that way would boot fine and also read back out of `GET /machines/<id>`. `fly secrets set -a <app>` first, then create. Adding the tenant to `computersFromEnv` is still a code change, and stays one until there is a third tenant.
- The guest's PID 1 is `apps/hub/src/host/init.ts` (root, via `guest-entrypoint.sh`): it supervises desk-up, one `eve start` per roster Bot, the WhatsApp bridge and the hub with restart backoff and health probes, and mirrors their state to `/run/computer/status.json`, which `GET /healthz` reports. `npm run up` runs `host/eves.ts`, which supervises the same Eve children the same way (`superviseEves` in `host/eve.ts` is the one launcher); the desk and the hub are docker compose and the foreground process there, so it starts neither. The WhatsApp bridge child is opt-in behind `COMPUTER_WHATSAPP=on`: `repoRoot` used to resolve one level short, so `bridgeDir` was `apps/apps/whatsapp-bridge` and the `existsSync` guard silently skipped the bridge on every guest. Turn it on once it has been watched starting, because `/healthz` reports the supervisor's view and `fly.toml` health-checks the guest on it.
- Every bearer resolves to one `PrincipalRecord` (`apps/hub/src/service/principals.ts`) through one `verify()`: a `user` at a seat, a `bot` holding an agent token, a `service`. A role is a set of methods (`ROLE_METHODS` in `packages/shared`); `owner` is unrestricted inside the Seat service and every narrower role is an allowlist, so a new RPC reaches owners immediately and nobody else until listed. `Seat.Issue` hands a named subject a seat: an owner may issue any role, an `issuer` (what a control plane holds instead of the setup code) may never issue `owner` or `issuer`. A record with a `display` is bound to that screen whatever its role. `Seat.Revoke {}` ends the caller's seat; sign-out calls it. The Eve proxy and `/roster` are owner-only. Bots and connectors keep their own files and are adapted into a principal at verify time; `seats.json` keeps its name and still reads both older shapes (a bare string, and `kind: owner | guest`).
- A connector (`apps/hub/src/service/connectors.ts`, `connectors.json`) is the third door: `POST /connectors/<id>/<path>` with `x-connector-secret` forwards to the Bot's Eve at `/eve/v1/<kind>/<path>`. The WhatsApp bridge uses it on loopback, but nothing in the ingress requires that: it never looks at the peer address, so a bridge on another host reaches it at the tenant's public URL unchanged. Never accept a seat token there. A connector is inbound and hub-minted; a plugin is outbound and human-consented, so the two words never merge. `channel` still means eve's own route file (`apps/eve/lib/channels/*`, `agent/channels/` in a bot dir) and the product sense, and neither was renamed.
- A conversation holds the exchange, not a note that one happened. The connector ingress resolves the conversation, records the inbound message, and records the Bot's reply through `ConversationRegistry.recordDelivery`, which no-ops when the turn already spoke through `send_message` so the tool's record wins and the transport's copy is not written twice. It used to resolve the conversation and leave it at `seq: 0`, which is why a WhatsApp thread was invisible to every client.
- `data/policy.json` missing means the shipped defaults (`ask` on package installs, `rm -rf`, `curl | sh`, and git/npm/eve under `/workspace/eve`), not an open box; write `[]` to opt out. Those four regexes only catch what someone named, so with `AI_GATEWAY_API_KEY` set a fifth default rule sends every other shell call to **Auto Review** (`service/auto-review.ts`, run through the existing `check` seam). It is additive and cannot loosen the four: `evaluate` takes the strongest decision across matching rules, so an `allow` from the reviewer never overrules the `ask` on `rm -rf`. It is also the one default with `fail_open`, deliberately: it sits in front of every shell call, so failing closed would turn a gateway outage into a box where nothing runs.
- A **coding session** is delegated, not run here: `service/coding.ts` hands a task and a GitHub repo to Cursor's Cloud Agents API and mirrors the run into a conversation with a `code` route, so the thread is the hub's and the work is not. That is the whole point. A harness under the supervisor would have its own shell and never cross `PolicyService`, Auto Review or the seat; `shell` caps at 120 s so a session cannot be an RPC; a worktree is not a boundary because the Machine is the only one; a session pins a Machine that should suspend; and a child started through `asBox` shares its uid with the model's `shell`, so its API key is readable out of `/proc`. Off by default: no `CURSOR_API_KEY` and the two Seat RPCs answer `DAEMON_DOWN`, as the WhatsApp ones do without a bridge. It is not a sixth model tool, and the on-box runtime for work that needs the box is not built (`docs/plans/coding-sessions.md`).
- `prepare` runs `lefthook install` only inside a git checkout. Vercel builds from a snapshot with no `.git`, and lefthook exits 1 there, which fails the whole install; keep the guard.
- The first run is a row, not a flag: `app/page.tsx` picks between the marketing page, the onboarding flow and the workspace, and `onboarding` (one row per user, written by `/api/onboarding`) is what says which. Skipping writes the same row with an empty answer, so a skip on a phone is not asked again on a laptop. The tools it asks about are a preference and never a connection: nothing there holds a credential or reaches a hub, and the answer's only job is to become the empty conversation's openers (`signInPrompt`, which asks for the seat rather than for a password). Adding the table to a deployment is `npm run db:push --workspace=apps/web`; there are no migration files in this repo.
- `apps/web` typecheck reads `.next/types`; a route you deleted can leave a stale reference until `rm -rf apps/web/.next && npx next build`.
- `apps/hub/test/eve-channel-auth.test.ts` is excluded from the hub tsconfig because it imports `apps/eve`; vitest still runs it.
- No Docker daemon in Claude Code on the web and similar sandboxes: `npm run up` uses the fake desk, and the desk image smoke test only runs in CI.
- **A Bot that nobody is talking to costs nothing, and that is what makes eight fit in 2 GB.** Measured idle, on the built QA project: `npx eve start` is 690 MB (npm shim 95, the eve CLI 367, the server it supervises 224), the built server run directly is 224 MB and boots in 0.7s, and a claimed window (Xvfb, openbox, x11vnc, Chromium) is about 430 MB. So production runs `node .output/server/index.mjs` rather than the CLI (`eveChildCommand`, with `npx eve start` as the fallback for an unbuilt dev tree), and both halves of a Bot are on demand: `ScreenKeeper` claims a window when something touches that display (`desk/lazy.ts` decides what "touches" means, and it is the X calls only, never `shell` or a file) and releases it after 30 minutes idle; the Eve child is registered asleep and woken through `host/wake.ts`. Keep the guest at 2 GB: it is Fly's ceiling for a suspendable Machine, and suspend-to-zero is the point. Idling out is not enough on its own, so both keepers have a ceiling (two screens up, two sleeping Bots awake, least recently used loses); raise those and the arithmetic stops holding. Two things follow from suspend that the docs must keep saying out loud: a routine only fires because something outside the box woke it (`apps/clock`, next bullet), and only a tree this build shipped may seed the roster, because `/workspace/eve/bots` is box-writable and would otherwise let the model mint itself a Bot, a token and a screen.
- **The wake protocol is a directory of small files, deliberately.** The hub cannot start Eve children (they are PID 1's, which is root and hands each a curated environment; moving that into the hub would put the setup code next to the model's uid), so the hub writes `/run/computer/wake/<bot-id>` holding the time that Bot may sleep again, and init's `watchWake` polls it every 2s and calls `ensure`/`stop`. The hub touches it on the `/eve/v1` proxy, the connector ingress and every one of that Bot's own tool calls, so a working Bot is never swept out from under itself. No socket, no port, no second credential; the directory is hub-owned 0770 and the model (box) cannot vote on whether it is awake.
- **A sleeping Bot cannot fire its own cron**, so a Bot with routines declares them twice: `agent/schedules/*.ts` is the routine, `agent/routines.json` is `{ id, cron }` for the hub, and `routineAlarm` wakes that Bot a minute before one is due so its own croner fires it. `apps/hub/test/routines.test.ts` fails when the two copies drift, which is the only thing keeping them honest. The cron subset is the one `cronMatches` understands (a star, a number, `a-b`, `a,b`, a step); anything else is refused rather than guessed at, because a cron nobody parses is a routine that silently never runs.
- **A Bot made at runtime has no directory, so it runs `apps/eve/bots/template`.** `Seat.CreateBot` mints a roster row, a token and a screen, and used to stop there: the supervisor plans its children from the roster at boot and a Bot with no project directory got none, so a created Bot answered `DAEMON_DOWN` forever. Three things fix that and all three are needed. `eveProjectCwd` falls back to the template project, which `eveProjectIds` skips so it never becomes a Bot of its own; `host/adopt.ts` has PID 1 poll the roster once a second and register a child for any Bot that was not there at boot (the hub cannot start children, same reason as the wake directory); and the `CreateBot` handler writes that Bot's wake marker, so it is running by the time the person who made it types. What makes two Bots on one project different agents is the profile, which the hub folds into the prompt: the name, the label and the description are the Bot. `MAX_DISPLAYS` was 8, exactly the number of Bots the build ships, so `CreateBot` on Blode could only ever answer CONFLICT; it is 16 now, and the cap that actually holds 2 GB is the two-awake, two-screens-claimed arithmetic, not the number of rows.
- **A suspended Machine cannot fire anything at all, so the outer clock is a separate app.** `apps/clock` (`fly.clock.toml`, one 256 MB always-on Machine for the whole fleet) GETs each tenant's public `/healthz` three minutes before any routine minute, because a request through Fly Proxy is what starts a suspended Machine and nothing inside the guest can ask to be woken. Three consequences. It must be the **public** hostname, never `<app>.internal`, for the same reason the bridge's `hub_url` is (6PN skips the proxy). A routine change is **two deploys**, the guest and the clock, because the clock reads the same `apps/eve/bots/*/agent/routines.json` out of its own image; `cronMatches` lives in `packages/shared` so both alarms answer "is it due?" identically, and a second cron implementation would be a routine one side fires and the other does not. And waking is not enough on its own: a routine turn makes no inbound traffic, so Fly Proxy would suspend the guest underneath it, which is what `busy` in the hub's `/healthz` (any live wake marker) and the clock's hold window are for. Fly's own alternatives were considered and do not fit: scheduled Machines are fuzzy interval buckets timed from machine creation, and supercronic in the image is stopped whenever the image is.
- **`fly deploy` builds from the working tree, so a local `eve build` breaks it.** `.dockerignore` must exclude `**/.output` as well as `**/.eve`: the guest image runs its own `eve build`, which renames any existing `.output` to a backup, and a local one copied into the context makes that rename EXDEV across the overlay and fails the image on the last step. Nothing catches it first: `.output` is git-ignored so a clean checkout never has one, and CI only runs hadolint over `deploy/fly/Dockerfile` and `deploy/clock/Dockerfile` (it builds the desk image, never the guest). Build it by hand before a deploy that matters: `docker build -f deploy/fly/Dockerfile -t expert-guest-verify .`

## Conventions

- Comments explain why, and the code around them is dense with them; match that density rather than adding what-comments.
- No em dashes in prose or comments; use commas, colons, or a new sentence.
- Errors on the wire are one envelope: `{ error: { code, message } }` with a code from `ErrorCode` in `packages/shared`. Throw `ComputerError`; anything else becomes a 500 `DAEMON_DOWN`.
- Secrets never land in `process.env` of a child the model can reach, in logs, or in an error message (see `ProvideSecret` in `apps/hub/src/service/voice.ts` for the pattern).
- Generated output under `packages/proto/gen` is committed; never hand-edit it.

## Do not commit

`data/` (roster and seat tokens), `.env`, `apps/web/.next`, `**/.eve`.
